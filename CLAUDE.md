# Tailscode — Agent Instructions

Native UIKit iOS client for remote coding agents (opencode + Claude Code via claude-bridge) over Tailscale. Thin shell over **CodingAgentKit** (`~/Dev/swift/CodingAgentKit`). Two desktop peers live in this repo: **TailscodeLinux** (GTK4) and **TailscodeMac** (AppKit, macOS 26+, Liquid Glass — read `TailscodeMac/AGENTS.md` before touching it; it carries the design contract, feature-parity rules, and the rsync+ssh build/selftest loop against `macbook`). Toolkit-free logic (shortcut registry, vim engine, slash completion, row state, status facts, stores) lives in **TailscodeCore** and is shared by all three clients — new capabilities go there first.

## Feature parity (enforced)

Three clients, one capability registry: `TailscodeCore/Sources/TailscodeCore/Parity.swift`. Every user-facing capability is an `AppCapability` case with a toolkit-free spec (`CapabilityRegistry`); each client answers every case in its own `Parity.swift` manifest with an exhaustive switch — adding a capability refuses to compile any client that hasn't decided what it does about it. **Any user-facing feature starts by adding/updating the case, and ends with all three manifests answering honestly** (`.implemented(anchor)` / `.partial` / `.gap(reason)` / `.notApplicable(reason)`). The Mac ships two ways — the ad-hoc build a person installs and the sandboxed one the App Store hands out — so its manifest may answer `.varies(direct:appStore:because:)` and the matrix has four columns, `mac` and `mac-store` reading the same file. `scripts/parity.sh` prints the matrix and greps every anchor through `scripts/lib/gating.awk`, which honours `#if TAILSCODE_MAS` so the store column cannot claim code it compiles out (`--check` gates; a Stop hook runs it). The `/parity` skill carries the full playbook and per-client validation loops. Never ship a feature to one client silently.

## Stack

- Programmatic UIKit, MVVM + `AppCoordinator`. No storyboards, **no SwiftUI** (except the Live Activity in `Tailscode/LiveActivity/`). Swift 6 strict concurrency, iOS 18+ / macOS 15+ baseline.
- Depends on `CodingAgentKit` (umbrella), `CodingAgentKitApple` (Keychain/profiles), and `AgentTestSupport` (DEBUG demo via `MockBackend`).
- Project generated by **xcodegen** (`project.yml`); Info.plist is generated (gitignored).

## Build / run (macOS only — iOS SDK)

Author on Linux, build on the Mac over Tailscale:

- `scripts/build-mac.sh` — rsync Kit + app to `macbook`, `xcodegen`, `xcodebuild` (simulator). Use to check compilation.
- `scripts/run-mac.sh` — build + install on an iPhone simulator + capture screenshots to `/tmp/tailscode-*.png`. Targets a specific device UDID (never `booted`, which is ambiguous when a visionOS sim is also booted).
- `--demo` launch arg → scripted conversation (no server), for screenshots. DEBUG env `TAILSCODE_HOST`/`TAILSCODE_PASSWORD` → auto-connect for a live session-list screenshot.
- `scripts/install-macapp.sh` — release-build TailscodeMac and replace `/Applications/Tailscode.app`. **This is the last step of any Mac work**, the same way `scripts/install-linuxapp.sh` is for Linux: a build that only ever exists under `build-mac/` is a change nobody can use, and the app launched from the Dock is the one that has to have it. `--tree <path>` / `--tree-constraints` / `--open <surface>` write any window's real geometry and Auto Layout ambiguity to a file, which is how a layout is checked without a screen.

## Develop the Linux client headlessly (never on the real desktop)

The desktop this repo is written on is in use. **Never open a development build on it** — `scripts/dev-linuxapp.sh` keeps ONE app alive on its own X display, its own session bus, and its own copy of the settings and data, and every command below reuses it instead of starting another:

- `start [--release] [--fresh] [--no-build] [--drive SCRIPT]`, `stop`, `restart`, `status` (rss/threads/fds/**window count**), `log [-f]`
- `shot [out.png]`, `click X Y`, `drag X1 Y1 X2 Y2`, `scroll up|down [n]`, `key ctrl+w v`, `type 'text'`
- `drive '2000:open=1;4000:splits'` (the app's own `TAILSCODE_DRIVE` verbs), `selftest`, `run <cmd…>` (anything inside the harness display + bus)

`DesktopGuard` enforces it: a binary under `.build/` exits 3 rather than render on a session it wasn't invited to (`--force-desktop` overrides).

## Shipping a change is part of making it (enforced)

A change that only exists in a build directory has not been made. **Every task that touches a client or a server ends by putting it on the machine it runs on** — not when asked, not when convenient, as the last step, every time:

- **Linux client → `scripts/install-linuxapp.sh`.** Builds release, installs, and restarts the app the person actually uses. Nothing else does this: the headless harness (`dev-linuxapp.sh`) and `swift build` both leave the installed binary untouched, so a passing selftest is not a shipped change.
- **claude-bridge → `swift build -c release` in `~/Dev/swift/claude-bridge`, then `systemctl --user restart claude-bridge`.** Never from inside a session running on that bridge — the restart tears down its cgroup and kills every agent with it (see [[claude-bridge-cgroup-self-restart]]); hand the two commands over instead when work is in flight.
- **Kit / Core** reach a client only through that client's own install, so a Kit fix is not delivered until the client carrying it has been reinstalled.
- **iOS / macOS** cannot be installed from this machine — say so plainly and name what the person has to run, rather than letting a green build read as a delivered change.

Report the version and pid the install printed. If an install is deliberately skipped — the work is server-side only, or the person is mid-session on that very binary — say which and why in the same breath as reporting the work done.

## Conventions (non-negotiable)

- `final class`; `@available(*, unavailable) required init?(coder:)` on custom views/VCs. Value types `Sendable`.
- No code comments, no MARK, no file headers. `///` sparingly.
- Design tokens via `Theme`. Route diagnostics through `AppLogger` (categories: lifecycle/connection/session/chat/streaming/persistence/ui), which fans to OSLog + `Library/Logs/tailscode.log`.
- The desktop app is one window, and a second launch asks to see it rather than to have another. The Linux client is single-instance on the session bus, so every later launch — the launcher, a terminal, an agent checking a change — remote-activates the process already running and arrives at `activate`; building a `MainWindow` there each time stacked a whole second app inside the one process (sidebar, tiling tree, terminal, polling timers, every session's stream) and released none of it, so both the window count and the memory only ever climbed. `activate` raises what exists.
- The iPad is a workspace, not a stretched phone. `WorkspaceSplitViewController` (`Tailscode/Shell/`) is its root: a sidebar of places (Home, Usage, Delegate, Video, Images), chat scopes (All, Live, Saved, Archived, one row per server) and pinned chats; the chat list beside it; and the conversation — or Home — filling the rest. The sidebar draws two facts differently on purpose, because both are true at once: the list's scope holds the selection, and the place open beside it wears the accent. A window too narrow for columns is the phone's app exactly — one stack, Home at its root — and the same view controllers are carried between the two arrangements (`arrange(collapsed:)`) rather than rebuilt, so a resize never closes a conversation: a chat in transit is marked `isChangingColumns` so leaving one stack is not read as the reader leaving it. Every chat open goes through `showConversation`, which replaces the conversation beside the list on a wide window and pushes on a stack everywhere else; the coordinator holds Home rather than finding it through the root. Width bands (`fitColumns`) decide how many columns show, a list column's rows start where the column can be seen (its view runs on under the floating sidebar; its cells may not), a press hands the keyboard to the column it lands in (`columnPressed`), a row dragged out of the list opens a window of its own, and a window the system restores reopens the conversation it was showing (`restorationActivity`). The iPhone never builds any of it.
- Home is one ranked board, and glass is only what floats over it. The first thing Home owes is what the whole of it adds up to (`HomeStatus` in Core: "1 needs you", "2 working", "All quiet", with what finished or failed today and which machine is down underneath, and a lead light in the activity vocabulary's own tone), and it is the first item of the list rather than the navigation title, so it survives a collapsed bar and the Duo's vertical one. Below it is one vertical list in `HomeBoard`'s bands — NEEDS YOU, WORKING, PINNED, SAVED, RECENT, each held to `HomeBandLimits` and dropped when empty, nothing scrolling sideways. The ranking is `groupIntoSections`, shared with the chat list and both desktops: what waits on the person leads, longest-waiting first (a turn stopped to ask, or work the machine found stuck); WORKING is ordered by when each conversation began and never by activity; a pinned chat that is busy or waiting is listed once, where it is busy or waiting, and wears its pin there. Every conversation is the same row (`ChatRowFacts` / `ChatRowContentView`) on Home, in the list beside a conversation and in a bookmark: the state glyph from `ActivityKind` in a tinted tile, the title with its unread dot, a news line only when something happened (`ChatRowNews`: what the agent is doing, what a waiting turn wants in `ApprovalAsk`'s words — a command, a file, or the question in the agent's own — how it ended, when a machine was last heard from; a settled, read chat says nothing), and who and where last. A chat that finished while the person was away says so on its own row and carries the unread dot; there is no section of notices. Beside a chat list (the iPad's wide and middle bands, a Duo page of the book) Home is Today: the list already holds every row, so the pane that is left holds the whole question each waiting agent is asking (`AskCard`) and the account's quota — whole cards in a tall pane, one `QuotaGlance` line in a short one — and with the list tucked away it is the phone's board again. The rows and bands are the content layer and are never glass (Home's cards used to be `UIGlassEffect` panes); glass is bar buttons, the composer, menus and sheets, the iPad sidebar and the Duo's vertical bar, the composer's container carries the system's scroll-edge interaction rather than a drawn fade, the only tint on Home is Send while there is something to send, and a short window (compact height) gives the composer's model pill back to the words. Home's bar carries one Tools button (new chat on a machine when there are several, Delegate, Video, Image); a render's ring-lit button stays in the bar while its light is lit, and the iPad keeps its pencil on the list. A project is an aim, not a place: the composer's destination chip opens `NewChatViewController` as the "New chat in" sheet (its menu of recent folders stays behind a long press), and a chat's own menu opens its project board.
- Chat rendering: one row per `MessagePart` (id `"messageID:partID"`), diffable data source with `reconfigureItems` for streaming growth.
- The row pressed is the row opened, and a chat names itself when it arrives. Home's list reorders are deferred while a finger is on it — the row pressed must be the row opened, because a paste-and-send aimed at one conversation must never leave from another — and a chat announces its title once when it arrives (and again, with a tap, when the row pressed is the chat already on screen), so a wrong open is never quiet. Every open, send, and queue decision logs the session it targeted. A queue belongs to the conversation, never to the surface showing it: `SendQueueStore` (Core) keeps every waiting message on disk keyed by profile and session, whoever shows that chat next reads it back, a pane that switches chats hands its queue to the store rather than carrying it into the next conversation, and a chat nobody is looking at still drains from a background watch (`SendQueueDrain.mayDrain`) the moment its turn yields — on iOS the launch walks the store and wakes a view model per held conversation.
- A message you sent is yours from the keystroke, and its ink says what became of it. A transcript is the *server's* account of the conversation, and a client that waits for the account to grow before drawing your words is a client that thinks about the Send key rather than answering it — in a conversation of a few thousand rows, rebuilding every row from every message is most of a second, and that second used to sit between the press and the words. So the words are drawn from what is already in memory: `PendingSend`/`PendingSendLedger` (Core) hold them, and a change to what this device is holding redraws **only the rows this device is holding** (iOS: `render` splits into a transcript rebuild and a `compose` pass, and `onPending` runs the compose alone; the desktops re-dock onto `lastFullRows`). The state is told by ink rather than by a word, and the ink changes only for a failure (`PendingSendReading.ink` → `.failed`): a message on the wire is drawn exactly as a sent one is, because the words are what matter and a bubble that fades in as the server takes it is a state nobody asked to watch; neither *sending* nor *sent* is ever written under it. A line appears only when the wait has become news (`caption` is nil until then — still sending past `slowAfter`, waiting for the machine past `quietAfter`, woken by `nextCaptionChange` rather than a ticking clock), and for the one state that had no face at all, *not sent*, carrying the server's own reason, still holding the words, and offering to send them again, edit them, or drop them. Nothing is ever yanked into the composer or the pasteboard for the reader to go looking in, and a failure retires on nobody else's message — only a send that arrived is reconciled away, by the user-message count it was written against. A queue that stopped draining behind a failure says `held` rather than wearing the same hourglass as a queue waiting its turn. A screen reader is told the state in words (`PendingSendReading.state`), because it cannot read ink.
- A sent prompt rises to the top, and the answer streams onto an empty page. Scrolled to its end, a transcript keeps the newest words at the bottom — the question just asked directly above the box it was typed in, the answer nowhere yet — when what a person wants is the question as a heading over a blank canvas, with the rest of the conversation one scroll up. The room is made rather than found: `FreshCanvas` (Core) is the arithmetic — pad the end of the transcript by the viewport less the prompt and whatever already sits under it, scroll in one animated motion to the offset that puts the prompt `headroom` under the top edge, shrink the padding as the answer grows into it, and hand back to ordinary follow-the-bottom the moment the end of the conversation meets the end of the window. The room stays when the answer ends — a short answer under its question is the page a person asked for, and snapping it back to the bottom would throw away the arrangement they just read — and goes only when the next send makes new room or the chat is left. One motion, never a jump and a correction; reduced motion lands at once; the server's row replacing the pending one does not move the prompt; a queued message, which has not gone, does not rise.
- An answer is written, not pasted. Text leaves a model in lumps, so the transcript plays it out of a buffer instead of painting each lump as it lands: `StreamCadence` runs at a speed that changes on a long time constant and may never drain the buffer faster than `CadenceTuning.floorTime`, so a model that pauses reads as a hand slowing rather than a frame dropping. Exactly one row — the last one, and only while the turn runs — is live. It is rendered **once per arrival** from the markdown-safe prefix (`CascadeGate` holds the *renderer*, never the reveal, at the last position where no inline token is half-open, so no answer flashes its asterisks) and the reveal then counts **rendered** characters, which is what makes the speed even. Everything past the reveal is laid out and drawn at zero alpha rather than cut off: the paragraph is measured when it arrives and never again, so no glyph moves after it lands and no line re-wraps under the reader — a frame changes colours, never layout. Setting a widget's text inside the frame clock's update phase measures it against the previous frame's allocation, which is exactly how a live row ends up wrapping at a stale width and running off its pane. The last `StreamCascade.span` rendered characters carry the wave (heat toward the theme's accent, a shimmer band travelling back on its own clock, a per-glyph entry fade from `entryFloor`); ultracode paints the edge with `Ultracode.rainbowStops`. Frames come from the display's own clock — `gtk_widget_add_tick_callback` on Linux, `CADisplayLink` at up to 120Hz on the Mac and iOS — never a chained timeout, which drifts against the compositor. The live row's widget is never rebuilt while it grows; history, a chat switch or a burst past the tuning is adopted whole; reduced motion reveals at once; and the wave must come off by hand when it lets go of a row, because a turn merely ending changes no row value for a diff to notice.
- Saved chats (`SavedChatStore`) are device-local and carry a full snapshot of each bookmarked conversation — a bookmark must still list and explain itself when its server is unreachable, its session deleted, or its profile removed. Never make the Saved list depend on a live listing.
- What a person decides about a conversation belongs to the server that holds it, so it follows them over the tailnet to every client and depends on nobody's account. Read, pinned, archived and saved are one ledger on the bridge (`marks.json`; claude-bridge 1.14, omp-bridge 0.8) stamped on every summary, so a change reaches every connected client as an ordinary list push within a second; `AgentSession.reportsMarks` tells *not pinned* from *this server cannot say* (opencode, an older bridge: the mark stays on the device). A press answers from the device and leaves a `MarkIntent` (`MarkIntentStore`, `PendingSaveIntent` for a bookmark) that outranks a listing until it is delivered and for a few seconds after; `SessionMarkSync` delivers it a second after the last press and again after every listing, each carrying the time the person decided, and the bridge keeps the later decision rather than the later arrival. `SessionMarks.reconcile` adopts what a server reports — from fresh listings and stream pushes only, never from `SessionListCache`, which describes an hour ago and would undo a press delivered since. The read mark is the bridge's own clock (the one `updatedAt` is read on), never a phone's. A chat held open in front of the reader is kept marked read as it grows (`keepRead` in each client's transcript), or it shows unread on every other desk while its answer streams. A server that begins reporting marks answers *not pinned* for every chat it has never heard of, so the first time a profile reports, the device's own pins and archives are offered to it (`SessionMarks.offerLocalDecisions`, the oldest possible decision where the device never recorded when) rather than erased by that answer; a pin or archive on a server that cannot keep marks says so once per server (`SessionMarks.deviceOnlyNotice`). A missed notice is settled by the read mark too (`ActivityInbox.isRead`): reading the chat on any desk clears it everywhere, never a question or an approval, and Clear reads the chats behind the finished news it clears so the dismissal travels too. There is no iCloud and there will not be one: Linux is a client.
- Coming back after a long absence reads the present once. `BridgeStream` drops its `epoch:seq` cursor when nothing was heard for 20 s and joins at the bridge's head with one resync and one list invalidation, because replaying the ring (8192 frames of text deltas and list moves) walked the screen through hours of work one frame at a time; a burst of list changes is gathered for 80 ms and folded into one merge, one sort and one board rebuild (`SessionListViewModel.flushPending`).
- An `AskUserQuestion` tool call is a question, not a tool row: it becomes a `QuestionCell` docked at the end of the transcript (`ConversationState.pendingQuestions`, derived from the transcript by `QuestionRequest.awaitingAnswer`). Claude answers by message, so the answer goes out through `ChatViewModel.send` — never a direct backend call, which a bridge busy with a live turn refuses.
- A compaction is a seam in the transcript, not a message: the `Compaction` part renders as a `CompactionCell` divider (rule + card, what was traded for what), with the CLI's own summary — tens of thousands of words of machine-facing prose — behind it in a reader, never inline. `/compact` always opens `CompactPreflightViewController` rather than firing bare; it is irreversible, takes minutes, and accepts an instruction for what the summary must keep.
- A turn that said nothing is an outcome, not a gap. A provider that refuses a request mid-stream ends the turn with no words, no tool call, no picture and no error — zero tokens and only the turn's own step markers — and because every transcript is built from what a turn produced, that outcome draws nothing anywhere: the spinner stops, the transcript sits exactly as it was, and the question reads as ignored. `ChatMessage.isAnswerless` names it in the Kit (assistant, completed, no error, not one part carrying content, and never a turn somebody stopped by hand), `AnswerlessTurnReading` writes the words once in Core, and all three clients draw the same card: what happened, the server's own finish word quoted when it adds anything, and — when the question carried pictures, the commonest thing a model is refused for holding — that fact and the remedy that follows from it. It claims no cause the transcript cannot show, holds perfectly still like every settled state, and offers exactly one action: the same words again, without the pictures where they were there, through the client's ordinary send. The words come from the prompt in the transcript rather than from a send this device happens to remember, so the card works on a conversation opened from another machine.
- A picture is something the agent hands you, not only something you attach. Every tool result that gives the model an image becomes a `file` part docked at the tool call that read it (bridge: `ImageResult` + `TranscriptFold`/`ClaudeRunner`), and the app renders it as an `ImageBubbleCell` captioned with its filename — the bytes come from the server over `/files/raw`, never as base64 through the transcript. Tapping one opens `ImageViewerViewController`, which is a gallery over every picture in the conversation rather than a single-image modal: paged, zoomable to 1:1 pixels, Live Text, and able to put the picture in Photos, the pasteboard, Files, or another app. A save must hand over the bytes the server has (`ImagePayload.exportData`), never a re-encode of the bitmap a bubble downsampled to display.
- Not idle is a state with a face, and it has one face on three desks. Every state that is not idle is a case of `ActivityKind` in Core, and the case carries the whole identity: an SF Symbol for the Apple clients, a one-column glyph for the text ones, one of four tones — live, attention, danger, quiet — a word for a band, a sentence for a screen reader, and a **motion**, which is part of the meaning rather than decoration. Work breathes on one slow swell; a turn that stopped to ask you something knocks twice and rests; something being turned over sweeps; and anything settled — failed, offline, queued, idle — holds perfectly still, because stillness is how a reader tells a stopped turn from a slow one. The swell is arithmetic in `ActivityMotion`/`ActivityPulse` read from the display's own clock as absolute time (`CADisplayLink`, `gtk_widget_add_tick_callback`), never a counter, so every badge on screen breathes as one hand and a row scrolled back into view arrives already in time. A frame may change light, and a sweep's single glyph; it may never change a size layout depends on. Reduced motion drops the movement and nothing else. A listing can only say that a turn is open, so a chat row says exactly that (`SessionRowState.activity`); a conversation this device is streaming is read down to what it is doing (`ActivityKind.inFlight`, `StatusFacts.activity`) — the tool that is out on the machine wearing that tool's own symbol, whether the answer has started arriving, a fan-out counted as agents rather than named as the call that spawned it.
- Between turns a process can still be working, and that is a face rather than idle. Claude Code starts a command or an agent in the background, answers, and hands the prompt back while the work runs — and speaks again on its own when it ends — so the conversation is neither running nor finished. claude-bridge reads the CLI's own `background_tasks_changed` level (replacing the whole set each time, ambient monitors left out) and reports it as `backgroundTasks`/`backgroundTask` on the session, its summary and its revision plus a `background` frame on the stream; the Kit carries it as `BackgroundWork` on `AgentSession`, `SessionRevision`, `TranscriptSnapshot` and `ConversationState`, adopted from every read of the record so a missed frame cannot leave a stale indicator; Core gives it one face (`ActivityKind.inBackground`, live tone, breathing) worn by the row (`SessionRowState.background` — WORKING, a BACKGROUND pill, the task's own words as the snippet), the streaming pane (`SessionPresence.background`), the status surface (`StatusFacts.Phase.background`) and the orb. `status` stays idle and the composer stays open, because the CLI accepts a prompt while it carries work; a running turn outranks it; a backend with no such notion never reports one and nothing is inferred.
- An ending is news until it is read, so a Live Activity outlives its turn. A card follows every turn of the conversation this device opened it for (`AppActivityController`, with every word and face from Core's `LiveActivityDetail`/`LiveActivityReading`): the next turn takes the same card back — sent from here, drained from the queue, or started by the machine itself, which claude-bridge announces by push — and a turn that ends settles the card in place instead of ending it: done with what it did and what the machine is still carrying, the question it stopped on, a failure, a cut-off or an empty answer, how long it ran and how long ago it finished. Opening the conversation is what reads it, so that is what takes it down, and a turn that ends on screen leaves nothing behind — on screen meaning that conversation's own surface in the app in front (`AppActivityController.shown`/`hidden`), never merely the app being open; a turn somebody stopped was never news to them, so its card goes at once, from the phone and the bridge alike; a card nobody came for leaves the Dynamic Island after `LiveActivityLinger.island` and the Lock Screen after `.lockScreen`, on the phone's clock and the bridge's alike. The card is the truth rather than this process's memory of it — a push may have settled or revived it while the app slept — so every decision reads what it shows, every local write carries its timestamp so a late push cannot paint over it, and a relaunch adopts the cards still standing (waking a watcher for a live one) instead of sweeping them away. Only a turn that began after the card settled takes it back, so a running state arriving late for the turn that ended — a stream catching up, a resync — cannot stand an ending back up. Between tools the card says thinking again, on the bridge as in the app. A token is an address, not a turn: iOS hands the app every standing card's token whenever another starts, so the app forwards only a token that changed and the bridge tells a card taken back for a new turn by its later start, or a settled card would forget it had ended and never leave the Dynamic Island. The server sends a detail key and never a sentence the widget has to show, because the phone writes the words in its own language; the keys are a wire contract with every installed app — added, never renamed — and the coarse phase beside them is the older contract, never extended.
- A turn that ends while the app is closed still says so, and nothing about it leaves the tailnet. Only a bridge holding Midgar's APNs key can push, so an App Store person on anything else heard nothing once iOS suspended the app; a relay would fix that by routing every ending through Midgar. Instead the phone hands the waiting to iOS: `TurnWaitCenter` holds one background `URLSession` (`com.guitaripod.tailscode.turnwait`) and, while the app is still in front (`sceneWillResignActive`, or a turn seen starting while inactive), arms one request per running turn that the server answers only when the turn ends or stops for the person — `GET /sessions/:id/wait` on claude-bridge 1.13+ and omp-bridge 0.7+ (a newline at once and every 10 s, then one `TurnWait` JSON whose `ending` is a `LiveActivityDetail` raw value; capped at 3 h with `running`), opencode 2.x's own `POST /api/experimental/session/{id}/wait` (204, outcome read from the transcript tail's `idle` item). opencode 1.x has no wait-without-sending route in any release and is an honest gap, never a blocking send in the background: nsurlsessiond re-sends a silent request, so **the background session never carries a request with a side effect**, and two identical waits at once are normal. The Kit vends the fully authorised request (`turnWaitRequest`, `turnWaitSupport`, `turnWaitResult`); the app wakes on the answer (`handleEventsForBackgroundURLSession`, work under `beginBackgroundTask`, the system's handler called last) and posts through `NotificationManager` with Core's words (`LiveActivityDetail.line`), settles the card and records the missed activity — once per turn end, whichever of the wake, the in-process watch or a bridge push got there first, and never while the app is in front. A dropped wait is unknown, never an ending: re-check, re-arm once, stay silent. `.undetermined` (transport, 401, 5xx) is never latched; a real `serverTooOld` is rechecked after 30 minutes. A bridge's push counts as covering a profile only when it said `delivers: true`. What a server can promise is Core's `TurnWaitAvailability` on the server screen; Background App Refresh off and a force-quit silence the whole mechanism, so Settings ▸ Notifications says so with the way back, and the footer says what is true of the wait itself: it runs straight over the tailnet, none of it through Midgar or Apple.
- A notification says what happened and can be answered from where it is. Facts cross the wire and sentences are written on the device: `NoticeWire` (Core, Foundation only, compiled by path into the notification service and the long-look extension, never linked) carries how long a turn took, how many tools it ran and what it changed, with the answer, the error, the command or the question as the server's own quote, and `NoticeWords` writes it in the reader's language, so a push from claude-bridge, a notice the app raises and the Linux desktop's read the same word for word. `NoticePresentation` sets how each kind is delivered (approvals and questions are time sensitive and rank highest, a finished turn is active) and what it wears; the iOS buttons follow what can be done: a finished turn takes a reply, a failure offers Try again, an approval wears Approve (which asks for Face ID) and Deny, and a question that offers options wears them as buttons through a pool of four question categories (`NoticeSlots`, kept in the app group because the service claims slots for pushes too; when the pool is full the oldest question loses its notice rather than keep buttons that now say something else). A reply or an answer typed into a notification goes through the same send as the chat's own, on the model and effort the chat is on, and a send that fails raises a notice with the words in it. Never ship a button that cannot act: a notice with no chat or no request wears the plain category. The long look is a content extension that reads only the notification, so it draws at once and offline. Design and mocks: `docs/ios-notifications.md`.
- A price is a conversation's, not a turn's, and it opens. The chat's own chrome carries what the whole session has spent (`SessionSpend`, `StatusFacts.spend`) rather than what the last answer cost, because one is a fact you act on and the other is a curiosity — and touching it opens the account: the total with turns/each/over/rate/tokens, a bar per turn against the priciest, where the money went across answer / cache written / cache read / fresh input, which model spent it, and the five most expensive turns named by the words that started them. The counting belongs to the machine that holds the transcript: the bridge reads the CLI's own JSONL for per-turn tokens by tier and prices them (`GET /sessions/:id/spend`), a backend that reports money per message is summed locally instead, and a server too old for either leaves the last turn's price where it was. The money is always marked an estimate and states its provenance — a subscription bills a flat fee, so the figure is API-equivalent value and never a bill. Every client draws the same five sections and decides only how tall a bar is.
- The month has numbers, they are the account's rather than a conversation's, and every model the person runs is in them. Each server already holds its own ledger, so each aggregates it once and Core's `UsageAnalytics` merges them into one account and generates every word: a Claude bridge prices every transcript turn by turn (`GET /analytics`, subagent sidecars included); an opencode server keeps a running total on every session record, which is the only ledger it can serve at a bearable size — one conversation's messages are megabytes of tool output and a month of them gigabytes, which is not a request to make of a phone — so `OpenCodeLedger` reads the records in one request. How much time is being read is the person's choice and it is remembered (`UsageWindow`): week, month, quarter or year, picked in the hero beside the number it qualifies, because a total with no window on it is not a fact. The grain follows from the span rather than being a second question — a day a column up to a month, a week a column for a quarter, a month a column for a year — so the chart is never 365 pins or seven columns of one week each; the heading and every bar's name follow the grain, the trend is measured on the days and named in the days it compared, and the week's rhythm is always read off the days themselves. The sections are the window's total with its per-day rate and trend, a bar per day, week or month with the quiet ones present, the week's rhythm Monday-first, the day's clock, providers, models, projects, tools, the four token tiers with what caching saved, the records worth telling someone about, per-machine shares when more than one server answered, and two or three insights. A client decides only how tall a bar is. Money is not the only yardstick, because a model on the server's own GPU costs nothing and still does the work: models and providers rank by the tokens they actually worked through — cache reads left out, being re-reads of text already counted once — a row that cost nothing reads *Free* beside its tokens rather than `$0` — but only for a door on the person's own machine (`ProviderIdentity.isLocal`); a hosted door the server has no rate for (Ollama Cloud on opencode, a gateway's free tier) reads *Unpriced*, because the bill exists and this ledger cannot see it — an account that spent nothing leads with the work instead of a zero, and a line under the models says how much of the window ran on a machine the person already owns, what was unpriced and through which door, along with what a list too long to draw left out. What a server could not measure is declared rather than implied (`UsageAnalyticsReport.Coverage`): a ledger of session records knows the money, the tokens, the model and the project and nothing about the turns inside, so the turn and tool clauses drop out of the wording rather than reading as zero, the clock and tool sections disappear rather than drawing empty bars, and the surface names the machine whose counts are missing. The money follows the spend doctrine — API-equivalent value, marked an estimate, never a bill — and a server too old for the route is named in the surface, never a silent hole in the numbers. The quota surface leads with the tightest window — the one that decides when the next send unlocks — and is the road to the analytics.
- The quota strip answers for everything on the board. Every provider the board shows gets a line — its tightest window, in the board's own order — walls first because they are the news, then the rest with the roomiest saying it is *still open*: a strip that listed only the hot windows read as the other providers having gone, and one that re-ranks by pressure moves the rows under the reader on every poll (`QuotaGlance.tightestPerProvider`).
- The quota board is the person's, and it holds still. Every server's report folds to one holding per provider (`QuotaRollup`), and what is shown of it, in what order and whether the tightest window leads is `QuotaBoardPreferences` (`QuotaBoardStore`, `tailscode.quotaBoard`, captured by `SettingsFile` on Linux): the default arrangement is the person's own order — never a sort by pressure that moves the cards while they are read; tightest-first and by-name are choices — and a provider hidden on the board leaves the details, the strip and Home's cards alike while a wall in front of the chat's own model still speaks in the chat, because that is a fact about the next send rather than a card. One row of switches names every provider the account reported and every one a client can only offer a key for; a card is moved from its own header; the details surface is a window of its own on the desktops, two cards across, rather than a popover the width of a phone. `QuotaBoard` does the arithmetic and a client decides only how a card is drawn.
- A compaction is over when its seam is in the transcript, whatever the stream said. The finish event is easy to miss — a phone suspended for the minutes a summarize takes, a stream reconnected past it — and every client gates its send queue on `ConversationState.compaction`, so a compaction nobody closed is a chat that quietly queues every prompt and wears "Compacting…" until it is reopened. `AgentConversation` counts the seams the transcript holds when a compaction begins and ends it the moment one more lands (a seam counts once its message is complete where the backend reports completion, so opencode's summary streaming into its seam does not end the card early); opencode's dangling marker is live only while it is the last thing in the transcript or followed by a summary still being written.
- The quotas are readable without opening anything, and one reading answers every size. `WidgetGlance` (Core, over `WidgetQuota` — the stored snapshot's own shape, since a widget process has no backend to ask) decides what every family says: walls first and the tightest window next, a full window drawn as **Used up** rather than 100%, money with no ceiling drawn as a **balance** rather than a bar at zero, an empty balance ranked as the wall it is, a size given only the rows it can hold and stating what it left out, and a snapshot nobody could refresh saying so before it says anything else — a percentage presented as current is the one lie this surface can tell. The widget is configured in the platform's own editor rather than by a rebuild (`UsageWidgetIntent`): which providers, read from the snapshot so the account's real providers are offered and one that stopped answering is not silently unpicked; how rows are chosen; how much each row says; where the colour comes from; whether the reset clock shows. Colour follows the app's theme through the app-group mirror (`ThemeSelection.mirrorSuiteName`) because an extension cannot see the app's defaults, but meaning outranks branding — a wall is the failure colour whatever was picked, and a tinted or Lock Screen rendering flattens to one ink without losing a fact. Every writer into the snapshot carries the money it was given (`usedUSD`/`limitUSD`/`currency`), and the extension refreshes itself inside its own budget instead of waiting to be opened.
- The tokens are a range, not a level, and every tank wears one grammar. A gauge says how full a tank is; the range says whether it will last, so a quota window is a **pace bar** — the solid fill is what has been used, the tick is where an even burn would be by now (how much of the window's time has elapsed), the hatched tail is where the fill lands at the pace so far — and words appear only when the tail has something to say (`PaceRow`, built by `QuotaPace` for a window and `ContextBurn` for the conversation's own, both Core). Tone follows where the fill lands and never how full it is: 90% with ten minutes to go is fine and 50% on day two of a week is the story. A glance surface (Home's strip, the desktop sidebar strip, widgets, the Lock Screen) draws a tail only when `tailIsNews`; an opened one (the usage board, the Range sheet) always does, and a row on pace is exactly as tall as it ever was. A projection is never stated as a fact: a window must be ≥ 10% and ≥ 15 minutes through its time, a reset the provider only estimates (`trustedReset == false`) makes every figure *about*, a rolling window (opencode's) has no span and so no pace (`QuotaWindowSpan`), a wall closer to the reset than `max(10 min, 10% of what remains)` is not news, and the rate is the last stretch's rather than the average once `QuotaTrail` (kept by `RangeStore`, one file under Application Support, fed by `RangeStore.observe` on every fresh quota report) has watched long enough. The conversation's own window says *about 8 turns* only from half full with three growths of history (`ContextBurn`; a compaction or any fall under 70% of the turn before restarts it) and names the biggest single turn beside it. The chrome speaks only when there is news (`RangeGlance` through `StatusFacts`): the context chip keeps its ring and swaps its share for turns left, a `wall` chip appears only for a window that governs the chat's model (`QuotaBinding.governs`) and will run out before it resets, a `cache` chip when an idle chat has outlived its prompt cache (`CacheWarmth`; the lifetime is the server's — `MessageUsage.cacheLifetime`, read off the cache writes the CLI made: an hour on one machine and five minutes on another — and the cost of going cold is said in tokens, never money) — all three open the one Range sheet (`RangeBoard`, `Action.range`), which replaces the context sheet on all three desks: a verdict sentence naming the tank that runs out first, the tanks that govern this chat as pace bars (windows that govern another model dimmed *not this model*), the cache countdown, what is in the window by content (`ContextComposition`: estimated shares scaled so they sum to the measured footprint, never presented as measured), footprint per turn with refills marked, Compact through its preflight. Home says one line when an account-wide window is on course to run out (`RangeHome`). *Running low* (`RunningLow`) is one plain notification per window per crossing, account-wide windows only, re-armed only after half an hour under 90% of the limit; the ledger lives in `RangeStore`, and a switch under Settings ▸ Notifications turns it off. Nothing here compacts, switches a model or holds a send. `docs/range.md` is the design and `docs/range-mocks/` the pictures it was argued in.
- The ledger is also a game, and Apple's Game Center wears it. The trophy catalog is Core's (`TrophyRoom`, scored inside `UsageAnalytics`'s own merge — `analytics.trophies`/`analytics.scores`), each trophy an identifier shared with App Store Connect, so the in-app card and Apple's dashboard can never disagree; `scripts/asc-gamecenter.py` mirrors the catalog into ASC (achievements, leaderboards, localizations, rendered SF-Symbol artwork) and a trophy added to `Trophies.swift` is added there in the same change, with achievement points kept inside Game Center's 1000-point budget (`TrophyTests` gates it). The analytics surface carries the case — earned count, the nearest unearned marks, the road into Apple's dashboard — and signing in is lazy and never a wall: the card renders whole from Core with no account, and reporting rides the fetches the app already makes, deduplicated per player so a refresh costs nothing (`GameCenterCoordinator` on iOS, `MacGameCenter` on the Mac). Game Center is Apple's account system, so Linux answers `.notApplicable` and the arithmetic stays toolkit-free in Core.
- A cue is a meaning, not an amplitude, and the wait is what it reports. Sending a prompt means waiting on another machine, so the cues that matter are the ones that carry the turn — `send`, `step`, `needsYou`, `received` (`HapticCue.Group.waiting`, which leads the list everywhere cues are shown). Nothing calls for an impact style: `Theme.Haptics` names what happened and `HapticEngine` plays the cue's composed Core Haptics pattern, and every recipe is authored to be **pleasant at the top of the slider** — a rounded body, a soft attack, at most one beat of reinforcement, sharpness kept low. A sharp stacked pattern reads as an alarm and none of these are alarms; volume is the user's dial, character is not. One setting (`AppPreferences.hapticIntensity`) scales every cue through `HapticStrength.drive`, reinforcement drops out below its `floor`, and repeats inside `HapticRecipe.minimumGap` are dropped so a burst of tool calls is felt as progress rather than a rattle. `HapticsViewController` is chosen by feel: the glass slider plays every stop it passes at the strength under the finger. Hardware without a Taptic Engine falls back to canned feedback that keeps each cue's meaning and says so.
- First run is a checklist the app verifies, not a form, and it is one plan on all three desks: Core's `FirstRunPlan` is the ordered rows (Tailscale on this device, your machine, connected) and every word in them, `FirstRunFlow` is the state behind them (probe, save, Claude's sign-in), and a client draws the plan and invents no sentence. The machine row offers three ways in, in this order — scan the code the computer printed (phones), open or paste a `tailscode://connect` link, and "I don't have a machine set up yet", which shows the one install command and waits for the machine — so nobody transcribes an address, mints a password or guesses a port; `ConnectLink`/`ConnectLinkPlan` read a link, which only ever prefills: the agent and port come from it, the machine is probed at once, a link for a server already added opens it, and its `key` is held back until the person presses Connect and never logged (`PairingLink.redacted`). A failed probe must name its cause and the machine and offer the one tap that fixes it (`ConnectDiagnosis` + `PortReachability`); never surface a raw `URLError`, and never tell anyone to check a port. Ask for a password only where the machine cannot trust the tailnet (`BridgeInstall.needsPassword`: claude-bridge from 1.7.2 needs none, omp-bridge and opencode do) and only once a server has said it wants one.
- A tailnet is a credential, and a password is the second key rather than the only one. Tailscale already authenticated every node with a device key and an account, so claude-bridge asks tailscaled who is on the other end of a connection (`TailnetGate`, `tailscale whois`) and admits a node signed into the same account as the machine without a password (`BRIDGE_TAILNET_AUTH`, same-user by default); a LAN neighbour, a local browser tab, a shared node or a tagged server is refused, and the password still opens the door for anything not on the tailnet. The clients owe two things (`AppCapability.serverAccess`, words in `ServerAccessReading`): where a server is explained, what let this device in — trusted through the tailnet as whom, let in by its password, or open — read from `ServerHealth.access` and left unsaid for a server that does not report it, because a guess reads as a fact; and a refusal that names the tailnet (`AuthChallenge.tailnetOnly`, read from the 401 body) is never written as a password prompt — no field is revealed, the diagnosis sends the person to Tailscale on this device, and a scan row says *its tailnet only* rather than *wants a password*.
- A signed-out Claude is a state, not a reply. The CLI answers every turn with "Not logged in · Please run /login" instead of failing, so the bridge reports the machine's account (`/auth`) and can run `claude auth login` on a pseudo-terminal; the app shows it as the warning banner in chat and the Claude account row on the server screen, and `ServerSignInViewController` splits the browser flow across the two machines — the server hands over the URL, the phone opens it and returns the code. First run reads it the moment the server is saved and opens this sign-in inside the checklist (`FirstRunFlow`, `.signedOut`). Never tell someone to open a terminal instead.
- Keeping the server current is the app's job, not an ssh session's, and one engine does it on every desk. `UpdateDriver` (Core) asks, presses and follows for all three clients — a client only says how to reach its machines and what its own app is — so the patience a restart gets, what a quiet line means and how a relaunch mid-update recovers cannot differ between desks. The bridge reports each update as a job (`ServerUpdate.Job`: an identity, the step — download, build, wait for idle, restart — and an outcome written by the process that came back after checking it runs the build the job made), and the driver follows exactly that job with every clock named in `UpdateFollowTiming`: a refused connection during the restart is the restart — and so is one that meets a restart press on a machine already waiting to load its build, which is followed back rather than reported as a press that never arrived — silence anywhere else is said to be silence rather than failure, a failure the transport describes is said in words rather than its dump of error domains, a relaunch asks the machine where the job got to instead of believing the ledger, and a job another device or the machine's own policy started is picked up the moment a check finds it. A bridge older than jobs is followed by its phases and given the outcome its versions prove. A bridge too old for the route, or a server that cannot update itself (opencode updates with its own command), says so and hands over the one line to copy.
- An update is a standing fact, not a notification, and what it brings is the news. Every machine in the picture — this app and each server it talks to — reports what it runs and what it could run, and the answer is one mark the app wears in its own chrome until the update is taken: a chip that says it in a word (`UpdateRollup.chip` — *Update*, *2 updates*, *Updating*, *Update failed*) beside the gear on Home, at the foot of the desktops' sidebars, and opening the update surface. It covers nothing, steals no focus, and has no dismiss gesture; setting an offer aside (`UpdateLedger.acknowledge`) keeps the press, drops the argument for it, and is recorded against *that exact offer*, so a newer release, a different obstacle or an obstacle that clears speaks again. The mark renders from `UpdateLedger` before any check of the launch completes and survives relaunches, and only the chip that says *Updating* moves. Every surface draws Core's `UpdateCard` and no client invents a word: the card leads with the product and both versions in the form a person reads (`VersionLabel` — `claude-bridge 1.9.2 → 1.10.0`, never a `git describe`), then **what is new** — the release notes the bridge reads from its project's own `CHANGELOG.md` at the head it would move to, falling back to the claim each commit subject leads with (`ChangeHeadline`) — then one press with the question it asks first; while a job runs the card is its steps (done, under way with a clock this device started, still to come, or where it stopped); and an update that landed is news for a day (`UpdateOutcome.isNews`): what it became, from what, whether anybody pressed anything, and what came with it. Every exact number and who reported it (`VersionFact.line`), the branch, the supervisor and the obstacle live in the card's details, one tap away rather than spoken over the headline. `UpdateReadings` still refuses to say anything it did not check — a server that never reached the project, one too old for the route, one that answered nothing, one that built but never restarted, and a store record that hasn't propagated are five states and none of them reads "up to date"; *current* expires while *behind* never does. One press does exactly what it promises (`UpdateInvitation.promise`): a bridge that can update itself is installed end to end and followed through its own restart, a machine that cannot is handed the one command, a phone hands its own update to the App Store outright, and a desktop that still has the checkout it was built from rebuilds itself through a detached script that guards every stage. "Update everything" walks the servers one at a time, never includes this app, which would replace the process doing the watching, and never a machine whose whole remaining job is loading a build it already has. `UpdateFixtures` seeds one machine in every state for a debug launch (`TAILSCODE_UPDATE_FIXTURES=1` or a list of `arch,mini,studio,pi,box,old`), which is how the cards are looked at without a fleet.
- A restart is how the new binary gets loaded, and it must never take a turn with it. Stopping the bridge tears down its whole control group, so every agent it started dies with it — and a check taken when a build *starts* says nothing about the machine four minutes later when it ends. The quiet test is therefore a barrier at the exit rather than a gate at the door: the bridge waits until nothing is running on that machine (`MachineQuiet` — a turn it is running, a transcript somebody is growing in a terminal, a sign-in halfway through its two-machine handshake, and never before the observer has counted once), flushes what it owes to disk, and only then exits. The wait is a state with a word (`waiting`, `UpdateProgress.Step.waitingForQuiet`) rather than a silence, and it is given up rather than held forever. A build that landed and was never started is one press (`UpdateInvitation.restartHere`) rather than a terminal instruction, and only where something would start the bridge again — a machine with no supervisor is handed the command instead, because a bridge that exits with nothing to bring it back is a machine no client can reach. What is in the way is named rather than summarised: the files that are dirty, the commits that cannot be fast-forwarded, the toolchain that would do the building — carried on `UpdateOffer.details` and deliberately outside the acknowledgement identity, so an agent writing one more file on that machine does not relight a mark somebody set aside.
- A machine can be trusted to keep itself current, and the trust is the server's rather than the device's. The policy lives on the bridge (`POST /update/auto`, off until somebody turns it on), so every client reads back the same answer and a phone nobody opens again does not stop a server updating. It takes an update only when it can finish the job end to end — a real supervisor, a clean checkout, a fetch that actually succeeded rather than counts left over from stale refs, and the same quiet barrier — and a commit that failed to build is not tried again until a newer one exists or an exponential backoff runs out, which it says in words (`UpdateAutomation.holdingOff`). A machine that will take the update itself is still shown as behind, because it is; it simply stops holding the standing mark up, since a mark is a request that somebody act and nobody has to, and its offer expires on that machine's own next look rather than standing all morning over a version installed at two. The switch renders from what the machine last answered, never from what this device last sent.
- A repository is read, never operated. Where a change lands is the one thing a transcript cannot tell you — which branch, how far it has drifted from its upstream, what the agent has already touched — so the server reads it (`GET /git`, porcelain v2 plus numstat, the recent commits, and any merge or rebase left half-done) and `GitState` arranges it once for all three clients: sections in the order a person triages in (conflicts, staged, changed, untracked), one row per path wearing git's own status letter and a tone from five meanings, a header that leads with the branch, and the chip the chat's chrome wears, which spells the tree out the way a prompt does (`↑↓` upstream, `✖` conflicted, `+` staged, `~` changed, `?` untracked) so it is read without being opened. A file opens its own diff, read into numbered lines by `GitPatchReader` so the same gutter is coloured on every desk. Nothing offers to stage, commit, pull or push: a change made from a phone is a change nobody reviewed on the machine that has to live with it. A directory outside version control says so; a bridge too old for the routes answers 404, which means *this server cannot say* and makes the surface disappear rather than fail.
- An empty pane is a question, not a caption. A split opens on `PaneChooser` (shared, toolkit-free): which server — named with its address, chat count and whether it is answering — then a new chat there or one of its recent ones, so the second pane can land on the other machine without touching the chat list. One server skips the question; the pane's own server is pre-focused. Keyboard-first (↑↓/jk, enter, 1–9, esc back) and clickable, and "New chat here" opens the new-chat flow with that server already chosen, into the pane that asked. Where the client has a live shell and the chosen server runs on this machine, the first row is "New chat in <folder>" (`PaneChooser.terminalFolder`, set by the window from `TerminalPane.standingDirectory` and kept current while the question is open), so `ctrl+w v` and Enter is a split without a directory browser; a pane that is asking owns the keyboard (`ChatPane.focusTranscript` leaves the composer alone while a chooser is shown), because a focused composer swallows every answer key.
- Where you press is what you are working in. On both desktops a press is routed from the window itself, before the widget under the pointer acts: the pane it lands in becomes the focused pane (accent, chrome, `ctrl+w` verbs), and a press in the chat list, file tree or terminal makes that the keyboard's region. It has to be routed from the toplevel — GTK menu buttons pop their popover on the press and never let an intermediate widget's capture gesture see it, and AppKit's first responder says nothing about which pane a click was aimed at. Nothing is claimed or made first responder: the press keeps its ordinary meaning, and a divider or the chrome between panes activates nothing.
- A pane can hold a page. `WebTarget` reads an address, a bare host, a port on this machine or words to look up, and the slot renders it inside the grid with the platform's own engine — WebKitGTK's view on Linux, `WKWebView` on the Mac, both plain widgets the tiling owns. It claims only the chords a browser owns (`ctrl+l`, `ctrl+r`, `alt+←→`, `ctrl+±/0`, esc) so every other key belongs to the page, wears the page's own title in its identity strip, and the layout snapshot restores the address it ended on. iOS has no tiling, so it has no slot.
- The terminal is how a split is aimed. `ctrl+shift+o` (right) and `ctrl+alt+shift+o` (down) open a split whose chat starts in the folder the terminal's shell is standing in, from any focus, so a `cd`, a `pushd` or a jump function is all the navigation there is. The folder is read from the kernel (`tcgetsid` on the pty names the shell, `/proc/<pid>/cwd`, the foreground job only when the shell cannot be read; `TerminalPane.standingDirectory`), never from the folder the conversation named and never by asking the shell, whose prompt may report nothing, and it belongs to *this* machine, so `TerminalSplit.plan` (Core, with every refusal's words) sends the chat to the focused pane's server when that server runs here, else the first local one that answers, else refuses aloud (`noLocalServer`). A terminal that runs one command at a time (no vte4; the Mac's pane) has no shell standing anywhere between commands and says so (`oneCommandAtATime`) instead of splitting into the conversation's folder. The new half is made first and filled while the chat is minted, on the pane that was split and never on whichever pane the focus has wandered to; it opens focused on its composer, so a `cd` typed next goes to the chat unless the terminal is refocused (`ctrl+shift+j`). The terminal is never told to `cd` where it already stands (`TerminalPane.setDirectory`), which would type over a half-written line or into the job it is running.
- A pane can hold a stream instead of a chat. `VideoTarget` reads a channel, a link or words and the slot plays it inside the grid: it splits, the dividers resize it, zoom hides its siblings, `ctrl+w c` closes it, and the layout snapshot restores what it was watching. Linux draws libmpv into the pane's own `GtkGLArea` — Wayland gives a client no way to put another window inside its own — while the Mac resolves the page with yt-dlp and plays it through AVKit; iOS has no tiling, so it has no slot. An empty slot asks what to watch in its own body, a playing one wears the stream's title in its identity strip, and `VideoCommand` answers space/m/e/arrows without taking keys from the chat panes. A player repaints its pane every frame and the split verbs share that machine, so the slot says so rather than letting it be discovered: `VideoNotice` is one wording in three widths — the chooser row that offers a stream carries the line, the empty slot carries the whole of it in a tinted card, and a playing slot keeps the short of it at the end of its identity strip until it is paused. It is a fact offered, never a warning, and it costs nothing to ignore.
- A preview is a picture the Mac makes and a client only draws. `previewd` (own repo, `guitaripod/previewd`) runs next to Xcode on a Mac: it builds the app with `xcodebuild` into a cache of its own, runs it on a simulator in a private device set (Simulator.app shows only the default set and takes over the framebuffer of whatever it presents, which would starve the stream, and nobody else's simulator is ever touched; it names its devices `pv-<id>` and deletes only those), streams the screen as it changes through `sim-video` from the idb release (pinned to a checksum, MIT; its stdin is held open on purpose because the tool reads the end of its input as the order to stop), and brings a change to the picture by the quickest road that works, which the strip names (`ReloadPath`: Updated in place, Rebuilt and restarted, Rebuilt from scratch) so a slow update always has a reason. The wire is `PreviewKit` in the Kit: JSON for the checklist and sessions, one length-prefixed stream of JPEGs, events and heartbeats (a still screen sends only heartbeats, so silence past 15 s is a dead link and never a still screen), and SSE for the session's own events; the wire types exist twice and are kept byte-identical. The simulator draws at most 60 pictures a second — every iPhone and iPad simulator measured reports 60 — so nothing here promises more, and how a screen feels at 120 Hz is a real device's to say. A picture is never blank: a change that does not build keeps the last good frame dimmed under a banner that says so in plain words with the compiler's first error one tap away, an app that closes is put back on the same screen by the host (three times in two minutes and it is left alone), and a host that stops answering is a state the runner recovers from with backoff, never an end. `PreviewRunner` (Core, never `@MainActor`) holds the picture and the news as two latest-wins mailboxes the pane drains once a frame from the display's own clock, attaches to the session already running for that app instead of starting another, and owns every task through a `PaneLifetime` so a parked or hidden pane owns no stream. `PreviewLight` is the face on the strip and wears the `ActivityKind` badges the strip already has: waking and reconnecting sweep, updating breathes, live, broken and offline hold perfectly still. A Mac is set up by a checklist the host proves (`DoctorCheck`: Apple silicon, Xcode, its license, an iPhone runtime, the streamer, disk) and the client draws, never by a form; each fixable row is a button for a job the host follows and the one thing a person must do by hand is install Xcode, so that row opens the App Store on the Mac. The host admits a request by its password or, on a tailnet, by the account the Mac is signed in to (the bridge's own gate), refuses to listen beyond loopback with neither, and stops a session nobody has watched for twenty minutes. The coding agent looks too: `previewd mcp` speaks the Model Context Protocol so an agent can see the screen it is changing, wait for its own edit to land and read the compiler's errors instead of guessing, and operate it — tap, drag and type reach the simulator as real HID events through the idb companion that ships beside the streamer. On Linux a removed key does not stay removed in the settings file, so `ForgeStore` clears by writing an empty value.
- The video button is a light, not a badge, and it says where the render is on every desk. `ForgeLight` (Core) reads the job into seven faces — dark, waking, waiting behind other jobs, rendering with how far, saving, a clip that landed that nobody has seen, a render that broke that nobody has read about — and `ForgeLight.frame` turns a face and an instant into strokes laid round the control's own edge (`ForgeRing`: fractions of the perimeter from the top centre, clockwise, never crossing the top), so a client only decides how a stroke is painted (`ForgeButtonRing` over a `tailscode_edge_*` cairo layer on Linux, `ForgeRingView` as shape layers on the Apple clients). The vocabulary is the activity one: a wake sweeps as a comet in the quiet tone, painted work is a live arc that fills clockwise with a light travelling along what is done (progress arrives in jumps, so `ForgeRing.follow` eases the arc and a ring never jumps with the census), a queue holds still, saving breathes, and a landed clip or a broken render holds perfectly still and stays lit until it has been looked at — the clip on a stage (the runner's `unpresented`), the failure on a card (`acknowledgeFailure`) — then fades. The runner exposes `light`; `present`/`acknowledgeFailure` tell the watchers on the next turn, because both happen inside a surface that is itself a watcher. Reduced motion drops the comet, the travelling light and the breathing and keeps the rest; a still face is drawn once and runs no clock. The ring replaced the activity badge on the button, so the spoken line (`ForgeLight.spoken`, `ForgeEntryPoint.accessibilityLabel(light:)`/`tooltip(configured:light:)`) is the only place the state is also said in words.
- Images and video are proven ready before they are used, and the proof is one answer. `MediaDoctor` (Core) asks a ComfyUI what it has (`/system_stats`, `/object_info`, `/models/<folder>`, the loaders' own choices as the fallback) and compares it with `MediaRequirements`, the catalog of every file and node class the graphs submit (a test holds it to the graphs; every file is public on Hugging Face at a pinned revision, `docs/media-setup.md`) — as a `SetupReport` of capability `media` whose check ids are stable keys and whose facts are names and numbers, with `MediaReading` writing every word. `MediaReadiness` holds one verdict per machine for thirty seconds so the video board and the picture studios never disagree (`ImageGenHealth` is that report reshaped), and a render that cannot work is refused in the doctor's words before it is posted (`ForgeClient`, `ImageGenRunner`), which also replace a raw node error. Why ComfyUI cannot be reached is six different sentences (`MediaVerdict.Comfy`): nothing listening, running for its own machine only (knowable only on that machine), silent, unresolved, something else, and starting — a socket that accepts while the process loads is never a failure and is asked again by the clock. A missing file's fix is the one `hf download` line for it, copied, never run: the files go onto the other machine and two licences need a person. The renderer is guessed from the agent server's host on 8188 (`MediaEndpointPlan`), asked silently when a surface first opens and filed against that server (`ForgeStore.endpoint(forProfile:)`) only once it answers, so a wrong guess never opens a picture lane. The test mock (`scripts/mock-comfyui.py`) can be put in each of these states by environment.
- The time is always in view and the world is one touch away, and it is one reading on both desktops. The chip at the foot of the sidebar (beside the Update chip, never hidden) carries the time here and a sky glyph — a sun climbing its arc by day, a moon crossing by night — and ticks once a minute on the boundary (`WorldClockReading.nextTick`), never faster; hovering it opens a glance that stays while the pointer is on the chip or on it (the pinned cities each with their offset, a strip of their own day from night to day with twilight ramps and a dot at their moment, the machines with how far each clock is from this one, the quota windows about to reopen) and clicking it opens Meridian, one lane per place on the viewer's day as a line of real minutes (`DayAxis`: a clock-change day is 23 or 25 hours), a line that is dragged to any minute so every lane reads its own time and day at that moment, the hours everyone is awake as a band, and the moment copied as ISO, UTC or epoch or told about (`ClockAlarm`, only while the app runs, and saying how late when the app was closed across it). Sunrise and sunset are computed from coordinates (`Solar`), so the day is right offline; machine clocks come from the `Date` header of answers the app already receives (`ServerClockLedger` in the Kit), cost no request and read *no reading* until something answers, and a machine far enough off carries a sentence about what it does to the chats it dates. Core owns every word and number (`WorldClockReading`, `MeridianBoard`, `ClockFormat`); a client decides only how a strip and a lane are painted. iOS answers `.gap`: it has no persistent foot and no pointer, and owes only a drawing. `docs/world-clock.md` is the contract and lists the fixture and drive hooks.

## Reality

- All networking/streaming/state lives in CodingAgentKit; the app only renders `ConversationState` from `AgentConversation.states()` and forwards user intent. If a capability is missing, add it to the Kit (it's the reusable core), not the app.

## Performance (measured, then kept)

- A transcript is rebuilt from every message on each state a conversation emits, which while a turn streams is every token, so nothing in a rebuild may cost the size of the conversation. Ask a tool call what it is with `summaryKind`, never `summary` (that parses the input and strips the whole output); read a path from `input`. iOS reuses each text part's split rows (`SegmentRowMemo`), the desktops reuse whole messages (`TranscriptRowBuilder`).
- The live row's markdown gate reads only what arrived (`CascadeGate.read` and its memo), and the prefix it hands back is found from the end.
- Linux `SettingsFile` writes only when a value changed, coalesced on its own queue, and `flush()` runs on every exit path. Nothing on a timer may encode the whole file on the GTK thread. `UpdateLedger.worthRecording` keeps a reading that only moved its clock from counting as news.
- The Mac transcript places its rows by frame (`TranscriptColumn`), each row's constraints ending at its own host: one stack of every row made each structural change — a body opened, a row arriving mid-turn, a batch of history — re-solve the whole page, 46–153ms for one expand on a 350-row chat, now 2–7ms. A chat is shown from its tail batch rather than once every batch is built, each pane keeps the last three chats' built pages, and a chat row the pointer rests on starts its conversation before the click. `TailscodeMac --bench <transcript.json …>` times open, expand, arrival and resize off the cached transcripts in `~/Library/Caches/Sessions` and checks the column against a stack row by row — a bench run without an ordered-out window prices every layout with a fresh engine and is wrong by 10–100×.
- Every `HTTPClient(policy:)` with the same policy shares one `URLSession`; bridge transcripts are read with `If-None-Match` and a 304 hands back the held copy (claude-bridge 1.11+).
- A picture is decoded once, off the main thread, and drawn from one shared preview. `ImageDecodeGate` is two wide (one from loaded) and decodes with GTK's own loaders, never through gdk-pixbuf's glycin subprocess; `PictureStore` holds the previews process-wide with relief and failure memory; landings are gathered into one row pass per frame; a picture widget never copies pixels (`tailscode_texture_scaled`, `tailscode_picture_with_intrinsic`). Under a GPU renderer it is a scaled texture node, under the cairo renderer a cairo node on the one attached surface.
- Nothing runs after the window is gone, and nothing stays busy while it cannot be seen. A quitting flag in the shim silences every posted callback, `Gtk.WeakWidget` holds every widget a timer or hop can outlive, `tearDown()` cancels the window's tasks, and pollers wait on `BackgroundGate` (window hidden or shed level raised). The sidebar draws through `RenderCoalescer`, spaced by the shed level.
- The app explains its own freeze: busy >= 0.9 for five seconds writes the main thread's backtrace and the five hottest threads to the log (`tailscode --stacks` resolves them), so a report starts from where the time went. `docs/linux-performance.md` has the measurements and the harness recipe.
- Numbers from the field: iOS logs `journey open`, `journey firstAnswer` and daily MetricKit summaries (hang and crash stacks under `Library/Logs/diagnostics`) in the `performance` category; Linux has `TAILSCODE_TRACE=1`.
