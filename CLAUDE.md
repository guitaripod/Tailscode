# Tailscode — Agent Instructions

Native UIKit iOS client for remote coding agents (opencode + Claude Code via claude-bridge) over Tailscale. Thin shell over **CodingAgentKit** (`~/Dev/swift/CodingAgentKit`). Two desktop peers live in this repo: **TailscodeLinux** (GTK4) and **TailscodeMac** (AppKit, macOS 26+, Liquid Glass — read `TailscodeMac/AGENTS.md` before touching it; it carries the design contract, feature-parity rules, and the rsync+ssh build/selftest loop against `macbook`). Toolkit-free logic (shortcut registry, vim engine, slash completion, row state, status facts, stores) lives in **TailscodeCore** and is shared by all three clients — new capabilities go there first.

## Feature parity (enforced)

Three clients, one capability registry: `TailscodeCore/Sources/TailscodeCore/Parity.swift`. Every user-facing capability is an `AppCapability` case with a toolkit-free spec (`CapabilityRegistry`, its table split across `CapabilityRegistry+*.swift` beside `Parity.swift`); each client answers every case in its own `Parity.swift` manifest with an exhaustive switch — adding a capability refuses to compile any client that hasn't decided what it does about it. **Any user-facing feature starts by adding/updating the case, and ends with all three manifests answering honestly** (`.implemented(anchor)` / `.partial` / `.gap(reason)` / `.notApplicable(reason)`). The Mac ships two ways — the ad-hoc build a person installs and the sandboxed one the App Store hands out — so its manifest may answer `.varies(direct:appStore:because:)` and the matrix has four columns, `mac` and `mac-store` reading the same file. `scripts/parity.sh` prints the matrix and greps every anchor through `scripts/lib/gating.awk`, which honours `#if TAILSCODE_MAS` so the store column cannot claim code it compiles out (`--check` gates; a Stop hook runs it). The `/parity` skill carries the full playbook and per-client validation loops. Never ship a feature to one client silently.

## Stack

- Programmatic UIKit, MVVM + `AppCoordinator`. No storyboards, **no SwiftUI** (except the Live Activity in `Tailscode/LiveActivity/`). Swift 6 strict concurrency, iOS 18+ / macOS 15+ baseline.
- Depends on `CodingAgentKit` (umbrella), `CodingAgentKitApple` (Keychain/profiles), and `AgentTestSupport` (DEBUG demo via `MockBackend`).
- Project generated by **xcodegen** (`project.yml`); Info.plist is generated (gitignored).
- The Kit is pinned by `Kit.version` in `TailscodeCore/Package.swift` and `TailscodeLinux/Package.swift`. On the author's machines the sibling working copy `~/Dev/swift/CodingAgentKit` is used instead, so a client change that needs a Kit change ships only after the Kit is tagged (no `v` prefix) and both `Kit.version` lines and `Package.resolved` files name that tag. `TAILSCODE_KIT_REMOTE=1` forces the published tag; packaging sets it so a release never builds from an unpublished working copy.

## Build / run (macOS only — iOS SDK)

Author on Linux, build on the Mac over Tailscale:

- `scripts/build-mac.sh` — rsync Kit + app to `macbook`, `xcodegen`, `xcodebuild` (simulator). Use to check compilation.
- `scripts/run-mac.sh` — build + install on an iPhone simulator + capture screenshots to `/tmp/tailscode-*.png`. Targets a specific device UDID (never `booted`, which is ambiguous when a visionOS sim is also booted).
- `--demo` launch arg → scripted conversation (no server), for screenshots. DEBUG env `TAILSCODE_HOST`/`TAILSCODE_PASSWORD` → auto-connect for a live session-list screenshot.
- `scripts/install-macapp.sh` — release-build TailscodeMac and replace `/Applications/Tailscode.app`. **This is the last step of any Mac work**, the same way `scripts/install-linuxapp.sh` is for Linux: a build that only ever exists under `build-mac/` is a change nobody can use, and the app launched from the Dock is the one that has to have it. `--tree <path>` / `--tree-constraints` / `--open <surface>` write any window's real geometry and Auto Layout ambiguity to a file, which is how a layout is checked without a screen.

## Develop the Linux client headlessly (never on the real desktop)

The desktop this repo is written on is in use. **Never open a development build on it** — `scripts/dev-linuxapp.sh` keeps ONE app alive on its own X display, its own session bus, and its own copy of the settings and data, and every command below reuses it instead of starting another:

- `start [--release] [--fresh] [--no-build] [--drive SCRIPT]`, `stop`, `restart`, `status` (rss/threads/fds/**window count**), `log [-f]`
- `shot [out.png]`, `click X Y`, `drag X1 Y1 X2 Y2`, `scroll up|down [n]`, `key ctrl+w v`, `type 'text'`
- `drive '2000:open=1;4000:splits'` (the app's own `TAILSCODE_DRIVE` verbs), `selftest`, `run <cmd…>` (anything inside the harness display + bus)

`DesktopGuard` enforces it: a binary under `.build/` exits 3 rather than render on a session it wasn't invited to (`--force-desktop` overrides).

## Shipping a change is part of making it (enforced)

A change that only exists in a build directory has not been made. **Every task that touches a client or a server ends by putting it on the machine it runs on** — not when asked, not when convenient, as the last step, every time:

- **Linux client → `scripts/install-linuxapp.sh`.** Builds release, installs, and restarts the app the person actually uses. Nothing else does this: the headless harness (`dev-linuxapp.sh`) and `swift build` both leave the installed binary untouched, so a passing selftest is not a shipped change.
- **claude-bridge → `swift build -c release` in `~/Dev/swift/claude-bridge`, then `systemctl --user restart claude-bridge`.** Never from inside a session running on that bridge — the restart tears down its cgroup and kills every agent with it (see [[claude-bridge-cgroup-self-restart]]); hand the two commands over instead when work is in flight.
- **Kit / Core** reach a client only through that client's own install, so a Kit fix is not delivered until the client carrying it has been reinstalled.
- **iOS / macOS** cannot be installed from this machine — say so plainly and name what the person has to run, rather than letting a green build read as a delivered change.

Report the version and pid the install printed. If an install is deliberately skipped — the work is server-side only, or the person is mid-session on that very binary — say which and why in the same breath as reporting the work done.

## Conventions (non-negotiable)

- `final class`; `@available(*, unavailable) required init?(coder:)` on custom views/VCs. Value types `Sendable`.
- No code comments, no MARK, no file headers. `///` sparingly.
- Design tokens via `Theme`. Route diagnostics through `MidgarLog` (MidgarCore.Logging): `MidgarLog.info("…", category: .session)` with the categories lifecycle/connection/session/chat/streaming/persistence/performance from `Tailscode/Logging/TailscodeLogging.swift` and MidgarCore's `.ui`, which fans to OSLog + `Library/Logs/tailscode.log`. The app, the widget and the notification service each call `TailscodeLogging.configure()` first, because an unconfigured MidgarLog writes `app.log`.
## Rules that break shipped users or machines

The reasons and the full designs are in `docs/agent-notes.md`.

- Pro and the tips are bought through `MidgarStore` (MidgarKit, pinned to an exact tag in `project.yml`), never StoreKit directly: `Shared/Midgar/TailscodeMidgar.swift` is the one composition root (Midgar ID, gateway client, store; no services in a test host, in the direct Mac build or in a screenshot launch that holds StoreKit back) and `ProAccess` is the one model the iPhone and Mac screens read (`isPro`, `products()`, `purchase`, `restore`). A second `Transaction.updates` listener would finish transactions the store has not queued for the ledger. `keychain-access-groups` lists the app's own identifier first and `cc.midgarcorp.shared` second: dropping the first strands every saved server credential. The StoreKit tests are `TailscodeTests` and only run on an iOS 27.1 runtime (`xcodebuild test -scheme Tailscode -destination 'platform=iOS Simulator,id=<iPhone Duo on 27.1>'`); the first purchase on a fresh simulator can stall, so stop it and rerun once.

- A carried conversation rides in the first message as `<carried-conversation …>` after the person's own words (`CarryMark`): the tag and its attributes are read by every installed app, added to and never renamed, and a client shows `CarryMark.split`'s `rest`, never the wrapped text. The brief is built on the device (`ConversationBrief`), prose only: tool output, reasoning and pictures never travel. A seam compares the pill's words, never ids, and `ModelSeamTracker` reads each settled answer once.
- The Agents board (`AgentTower`) holds nothing while closed and watches at most six running sessions through the backends the client already holds, never a connection of its own. An approval on it shows the whole command, never its first line; a Claude question or a server with no queue answers `.needsChat` and the client opens the chat. A step's age is when this device first saw it, never how long it took. A Live Activity tap keeps opening its chat.
- Wire contracts: Live Activity detail keys are a contract with every installed app, added and never renamed, and the coarse phase beside them is never extended. The server sends a detail key (`LiveActivityDetail`), never a sentence a widget has to show.
- Background turn wait (`TurnWaitCenter`, `com.guitaripod.tailscode.turnwait`): the background `URLSession` never carries a request with a side effect, because nsurlsessiond re-sends a silent request. opencode 1.x has no wait route and gets no blocking send. A dropped wait is unknown, never an ending, and `.undetermined` (transport, 401, 5xx) is never latched. Nothing about a turn ending leaves the tailnet.
- A Claude `AskUserQuestion` answer goes through `ChatViewModel.send`, never a direct backend call (a bridge busy with a live turn refuses it). `/compact` always opens `CompactPreflightViewController`: it is irreversible and takes minutes. A subagent is never its own chat: never push or present a `ChatViewController` for one.
- Bridge restarts: a restart must never take a turn with it, because stopping the bridge kills its whole control group. The bridge exits only after `MachineQuiet`, and a machine with no supervisor is handed the command instead of a restart press. "Update everything" never includes this app and never a machine that is only loading a build it already has. `UpdateReadings` never says "up to date" for something it did not check. Versions read as `VersionLabel`, never a `git describe`.
- Core runtime types are never `@MainActor` (`g_application_run` does not drain libdispatch's main queue, so an await on it hangs silently): `PreviewRunner`, `VoiceCallSession`, `SetupDesk` and the rest. A client gives Core its own `HostClock`.
- A transcript rebuild runs on every streamed token, so nothing in it may cost the size of the conversation: ask a tool call `summaryKind`, never `summary`, and never in a loop over a transcript. Nothing on a timer may encode the whole Linux `SettingsFile` on the GTK thread. Pictures decode through GTK's own loaders, never gdk-pixbuf's glycin subprocess. A `TailscodeMac --bench` run without an ordered-out window is wrong by 10-100x.
- Linux is single-instance on the session bus: `activate` raises the existing window and never builds another `MainWindow`.
- Saved chats (`SavedChatStore`) never depend on a live listing. `SessionMarks.reconcile` adopts marks from fresh listings and stream pushes only, never from `SessionListCache`, and the read mark is the bridge's clock, never the phone's. A queue is changed only through `ConversationQueue`, never by saving a held copy.
- Connect and setup: never surface a raw `URLError`, never tell anyone to check a port or to open a terminal. A capability that is not ready is a checklist the machine proves, never a toast that says to run a command. A pairing link's `key` is never logged (`PairingLink.redacted`), and a link on the pasteboard is offered and never used. Image bytes come over `/files/raw`, never as base64 through the transcript.
- Money: spend and quota figures are API-equivalent estimates, never a bill, and a projection is never stated as a fact. Delegation is part of Pro but never the general sheet's lead (`DelegateProGate`, `ProOffer.perks`); the direct Mac build and Linux sell and gate nothing, and the demo world is never behind the price.
- Voice call: the client never plays the model's audio and never leaves the microphone open after a call. GPU figures come from `VoiceRequirements`, never typed into a string. A missing media file's `hf download` line is copied, never run.
- A feature leaves beta by deleting its `BetaFeature` case, never by hiding it.

## Reality

- All networking/streaming/state lives in CodingAgentKit; the app only renders `ConversationState` from `AgentConversation.states()` and forwards user intent. If a capability is missing, add it to the Kit (it's the reusable core), not the app.
